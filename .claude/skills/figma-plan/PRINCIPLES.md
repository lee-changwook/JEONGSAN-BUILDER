# Figma 구현 계획서 작성 원칙

## 1. 계획서의 목적

소비자는 `execute-figma-plan` 스킬 (Claude 자동 구현).
모호함 없이 구현 가능한 수준의 구체성을 갖춘 기계 실행 가능 명세를 작성한다.
사람이 읽기 좋은 문서가 아니라, 구현 에이전트가 추가 질문 없이 실행할 수 있는 문서.

## 2. 컴포넌트 분해 원칙

- 단일 책임: 하나의 컴포넌트는 하나의 역할
- Figma 프레임 구조를 그대로 컴포넌트로 매핑하지 않음 — 시각적 그룹핑과 논리적 컴포넌트는 다를 수 있음
- 재사용 가능성 판단: 같은 구조가 2회 이상 반복되면 공용 컴포넌트로 분리
- 컴포넌트 분해 테이블에 모든 UI 요소를 빠짐없이 매핑

## 3. 구현 순서 결정 원칙

- 의존성 역순: 의존받는 것(공용 컴포넌트, 타입 정의)부터 먼저
- 레이어 순서: shared → entities → features → widgets → page
- 스타일보다 구조 우선: 레이아웃 뼈대 → 세부 스타일링
- 각 단계에서 "어떤 파일에서 무엇을 만드는지" 명시

## 4. 프로젝트 컨벤션 비종속 원칙

- 계획서에 특정 스타일링 솔루션(Emotion, Tailwind, CSS Modules 등)을 하드코딩하지 않음
- "스타일 파일", "디자인 토큰"처럼 추상적 용어 사용
- 프로젝트별 컨벤션 적용이 필요한 곳에는 "프로젝트 컨벤션은 CLAUDE.md 또는 프로젝트 규칙 파일을 참조하여 적용한다"라고 안내

## 5. 디자인 토큰 매핑 원칙

- Figma 변수(색상, 타이포그래피, 간격)를 반드시 계획서에 기록
- 프로젝트의 기존 토큰 시스템과 매핑 가능한지 판단 → 매핑 테이블 포함
- 매핑 불가한 토큰은 "신규 토큰 필요"로 명시
- figma-analyzer가 제공하는 디자인 토큰 분석 결과를 누락 없이 반영

## 6. 에셋 처리 원칙

- Figma에서 추출된 이미지/아이콘 URL(localhost URL 포함)은 그대로 보존
- 플레이스홀더 이미지 생성 금지
- 새 아이콘 패키지 임의 추가 금지
- 에셋 URL 목록을 계획서에 빠짐없이 기록
